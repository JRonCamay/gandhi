# Success Log 260706_000001

## Task

Fix Transfork snapshot drag so the blue transform box follows the temporary sprite snapshot during drag.

## Problem

During sprite drag mode, the snapshot moved immediately but the blue transform box stayed behind or returned to the original sprite bounds.

## Root Cause

The transform box rectangle was owned by `updateSelectionBox()`, which runs every animation frame and rewrites `overlay.style.left`, `overlay.style.top`, `overlay.style.width`, and `overlay.style.height`.

Earlier attempts made `snapshotDragPixel.js` write the overlay directly, but those writes were overwritten by `updateSelectionBox()`.

## Failed Approaches

- Making `snapshotDragPixel.js` directly move the transform box.
- Adding repeated late overlay writes from drag-side code.
- Trying to race the animation loop instead of changing the owner input.

## Winning Approach

Keep `updateSelectionBox()` as the single transform box owner.

During active snapshot drag, make `updateSelectionBox()` read `window.Transfork.snapshotDrag.state.rect` plus `state.screenDelta` as the source of truth for the overlay rectangle.

Outside snapshot drag, continue using the existing idle pixel rectangle path.

## Why it Worked

Only one function writes the final transform box rectangle.

The drag module provides state; the box owner renders that state.

This removes competing overlay writers and avoids animation-frame race conditions.

## Files Modified

- `transfork-main.js`
- Function: `updateSelectionBox()`

## Reusable Engineering Rule

Patch the owner, not the competitor.

One behavior should have one final writer. Other modules should provide state, not fight the owner with parallel writes.
